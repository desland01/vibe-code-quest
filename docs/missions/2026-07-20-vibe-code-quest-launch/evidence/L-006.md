**`resolveTier` correctness note.** The old condition was
`status === 'trial' || (window is open)`. Two real defects fell out of it, both fixed here:

- Billing writes status `trialing`, never bare `trial`, so the status arm never matched
  anything the billing code actually produced.
- The date arm had no status guard, so a **canceled** entitlement with a future
  `trial_ends_at` still resolved to `trial` and inherited elevated daily caps.

New condition: `(status === 'trial' || status === 'trialing') && starts_at <= now < ends_at`.
Everything else resolves to `free`, which is allowed under free caps. Locked by
`src/__tests__/access.test.ts` with three cases — expired, active, canceled-with-future-window.

## 3. Known failure observed and attributed — `e2e/onboarding.spec.ts`

The first full-suite run of this session was **49/50**: `onboarding.spec.ts` failed waiting for
"Map unlocked" (5 s expect timeout). It then failed 3/3 when run solo, which is *not* the
documented parallel-load flake, so it was investigated rather than retried.

**Root cause: Neon round-trip latency while the database is cold, not a code change.**

- Measured directly against the running server: with a cold pool the `POST /api/onboarding`
  answer took **5–7 s** (server-side `application-code` timing from the dev log); once warm the
  same request took **2.47 s**, comfortably inside the 5 s expect.
- The answer path is round-trip heavy: `loadState` → `parseAnswer` (`checkAccess` including an
  `expireStaleReservations` transaction, plus `reserveUsage` with advisory locks) → the locked
  `withUserTransaction` → `generateQuestionText` (`checkAccess` + `reserveUsage` again). Each
  Neon hop measured 0.2–2.1 s cold.
- Once the pool was warm the spec passed solo (11.3 s) and the **full suite passed 50/50**.

**Not caused by L-006.** The onboarding surface executes the same number of database
round trips before and after this slice. The one query L-006 removed from `decide()` was behind
a `surface === 'guide'` guard that the onboarding path never entered; `resolveTier` changed its
boolean logic but issues the identical single query.

Per KICKOFF §6 and the standing guardrail, **timeouts were not bumped**. Recorded here as an
environment-dependent slowness, and carried into the L-011 QA-MATRIX.

**Flagged for later, deliberately not fixed here:** when `AI_GATEWAY_API_KEY` is absent,
`generateWithGateway` returns `gateway_down` immediately (`src/server/ai.ts:99`) — yet the
caller has already paid for a full `checkAccess` + `reserveUsage` cycle, twice per answer. That
reservation work is pure waste whenever the gateway is known-unavailable. Changing it touches
the access seam, so it belongs to L-009 or later, not to this slice.
