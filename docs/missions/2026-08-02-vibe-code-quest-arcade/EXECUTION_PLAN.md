## The one rule that orders everything

**Enforcement before content.** The architect's top risk (CREATIVE_BIBLE §8.5) is that 96 new runs written by many agents without mechanical voice enforcement drift back into the exact word salad this mission exists to kill. So the word-budget test, the banned-phrase test, the stage-fit test and the tier-aware provenance test all ship and go green **before a single new run is authored**. A milestone that writes content before its guard rails exist is mis-sequenced, not fast.

**Corollary:** the first content island is written *by hand, slowly, by the copywriter tier* and becomes the reference corpus. Fan-out only happens against a proven pipeline and an approved voice sample.

## Execution rules

**Serial by default.** One worker, one slice, one issue, one structured handoff.

**The one fan-out, and the rule that makes it safe.** Per-island content in M4–M6 looks disjoint, but both reviews found it is not: [`src/content/index.ts`](../../../src/content/index.ts) imports all 48 modules into one registry, and the manifest build reads every region. Island content files are disjoint; the registry, `regions.ts` and the generated manifest are **shared and contended**.

The ownership rule: island workers write **only** under `src/content/<island>/`. They never touch `index.ts`, `regions.ts`, `schema.ts`, or the manifest. A single integrator — the orchestrator — makes every shared-file edit, serially, after each island lands. A worker that needs a registry change stops and hands back rather than editing it.

Fan-out also runs *behind* the approved voice reference from M1b/M2 and the enforcement suite from M1a. That is what stops eight parallel authors producing eight different voices.

**Never parallelise:** the content model (M1), the stage shell (M2), the audio engine (M2), or the migration (M7). Each is a single coherent surface where two writers produce a merge conflict or, worse, a silent inconsistency.

**Every slice ends with a structured handoff:** completed / undone / files touched / commands run with exit codes / issues found / next slice.

**Validators never share worker context.** Scrutiny (spec + gate), User Testing (live behaviour at the locked stage, keyboard-only path, reduced-motion path), Handoff (blocks an underspecified handoff).

**Visual proof is rendered proof.** Per project `CLAUDE.md`, a green build is not visual evidence. Every UI slice ends with a rendered screenshot reviewed by the vision tier.

## Stop conditions

Execution halts and returns to the owner on any of:

1. **Spend** — none is planned. Any proposal to buy audio, art, or a service stops here.
2. **Deploy** — nothing in this mission ships to production. Promotion is a separate approval.
2b. **Live database mutation.** `npm run test:db` and `npm run test:rls` are in the definition of done, and [`scripts/with-neon-branch.mjs:76-77`](../../../scripts/with-neon-branch.mjs) creates a real branch in a hard-coded Neon org and project whenever `TEST_DATABASE_URL` is unset. **That is a live external mutation and it was mis-declared as safe in the first draft of this packet** (adversarial finding F-005). Running the DB gate requires either a proven disposable or local `TEST_DATABASE_URL`, or recorded owner approval for the branch operation. A preflight must refuse otherwise, and a cleanup failure fails the gate rather than warning.
3. **The 8×6 shape** — if any slice concludes the region/landmark counts must change, stop. That is a content-architecture decision, not an implementation detail.
4. **The frozen design contract** — the 2026-07-19 contract is inherited, not reopened. A slice that needs it unfrozen stops.
5. **Existing player data** — any migration step that cannot preserve totals exactly stops before writing.
6. **The M3 gate** — content fan-out cannot begin on an unapproved voice.
